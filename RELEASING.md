# Releasing LightlyTrain

This document describes how a release is cut. See
[CONTRIBUTING.md](./CONTRIBUTING.md#pull-requests) for the pull request title convention
that this process builds on.

The actual publishing steps (PyPI, documentation, DockerHub) live in the private
`lightly-train-private` repository and are triggered manually against a tag of this
repository.

## Current Process

Releases are prepared by hand up to and including `0.18.0`.

1. Open a release pull request that:

   - Renames the `## [Unreleased]` section in [CHANGELOG.md](./CHANGELOG.md) to
     `## [X.Y.Z] - YYYY-MM-DD` and inserts a fresh, empty `## [Unreleased]` section
     above it with the six [Keep a Changelog](https://keepachangelog.com/en/1.1.0/)
     headings (`Added`, `Changed`, `Deprecated`, `Removed`, `Fixed`, `Security`).
   - Bumps `__version__` in `src/lightly_train/__init__.py`. This is the single source
     of truth for the version; `pyproject.toml` picks it up via
     `[tool.setuptools.dynamic] version = {attr = "lightly_train.__version__"}`.
   - Updates the "News" lists in [README.md](./README.md) and `docs/source/index.md`.

1. Merge the release pull request and tag the resulting commit on `main` as `vX.Y.Z`.

1. In `lightly-train-private`, run the `Release PyPI`, `Release Documentation`, and
   `Release DockerHub` workflows via `workflow_dispatch` with that tag as input. All
   three assert that `__version__` at the tag matches the tag name, so the bump and the
   tag must agree.

## Planned Process From 0.19.0

Pull request titles have followed
[Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) since `0.18.0`,
and because pull requests are squash merged the history of `main` is now machine
readable. From `0.19.0` onwards, the version bump and the changelog will be generated by
[release-please](https://github.com/googleapis/release-please) instead of written by
hand.

The release flow then becomes:

1. release-please keeps a release pull request open on `main`, updating the version and
   the changelog on every merge.
1. Merging that pull request creates a **draft** GitHub release. The git tag is not
   created yet.
1. Edit the release notes on the draft, then publish it. Publishing creates the `vX.Y.Z`
   tag.
1. Trigger the release workflows in `lightly-train-private` with that tag, exactly as
   today.

### Configuration to Add

`.release-please-manifest.json`:

```json
{ ".": "0.18.0" }
```

`release-please-config.json`, with `changelog-sections` mapping the commit types onto
the Keep a Changelog headings already used in `CHANGELOG.md`:

```json
{
  "$schema": "https://raw.githubusercontent.com/googleapis/release-please/main/schemas/config.json",
  "packages": {
    ".": {
      "release-type": "python",
      "bump-minor-pre-major": true,
      "draft": true,
      "changelog-sections": [
        { "type": "feat", "section": "Added" },
        { "type": "fix", "section": "Fixed" },
        { "type": "perf", "section": "Changed" },
        { "type": "refactor", "section": "Changed" },
        { "type": "docs", "section": "Changed", "hidden": true },
        { "type": "test", "section": "Changed", "hidden": true },
        { "type": "build", "section": "Changed", "hidden": true },
        { "type": "ci", "section": "Changed", "hidden": true },
        { "type": "chore", "section": "Changed", "hidden": true }
      ]
    }
  }
}
```

`bump-minor-pre-major` keeps breaking changes on the minor version while the project is
below `1.0.0`, so `feat!` gives `0.19.0` rather than `1.0.0`.

`.github/workflows/release_please.yml` runs `googleapis/release-please-action@v4` on
pushes to `main` with `contents: write`, `issues: write` and `pull-requests: write`
permissions.

The `python` release type resolves `src/lightly_train/__init__.py` from
`name = "lightly_train"` in `pyproject.toml` and updates `__version__` there. Its
`pyproject.toml` updater detects `dynamic = ["version"]` and skips the file instead of
failing, so the build configuration needs no change.

### Known Adjustments Required at That Point

1. **mdformat must stop reformatting the changelog.** `MDFORMAT_FILES` in the
   [Makefile](./Makefile) currently includes `*.md`, which covers `CHANGELOG.md`, and
   `make format-check` runs in CI. Generated changelog output is not mdformat-clean, so
   `Check Code Format` would fail on every release pull request. The installed mdformat
   has no `--exclude` flag, so replace `*.md` with an explicit list of the root Markdown
   files that should still be formatted (`README.md CONTRIBUTING.md RELEASING.md`).

1. **`docs/prebuild.py` must accept the new changelog headers.** `build_changelog_html`
   matches `## [0.17.0] - 2026-07-28` to insert the `(changelog-0-17-0)=` MyST anchors
   that [README.md](./README.md) and `docs/source/index.md` link to. release-please
   writes `## [0.19.0](https://github.com/.../compare/v0.18.0...v0.19.0) (2026-xx-xx)`
   instead, so the version pattern has to match both shapes or the anchors are silently
   lost. The `[Unreleased]` stripper in the same function becomes a harmless no-op.

1. **Release pull requests will not trigger CI.** GitHub does not start workflows for
   pull requests opened with the default `GITHUB_TOKEN`, so required checks stay pending
   on the release pull request. Closing and reopening it by hand triggers them. If that
   becomes tedious, mint a token with `actions/create-github-app-token` and pass it to
   the action instead.
